# diffharness

## What is it?
`diffharness` is RinDB's differential testing harness. It drives both a RinDB instance and a SQLite-backed reference implementation through the same engine interface so they can be exercised in lockstep while exposing identical transaction, CRUD, range, and snapshot primitives. Every operation and phase transition is streamed to a JSONL log, giving a reproducible trace of each fuzz run.

## What is its purpose?
The harness continuously compares RinDB's behaviour with the oracle to surface correctness bugs, recording mismatches with enough context to replay them. Each operation is executed against both engines; any divergence raises a detailed mismatch error, and the operation log can be replayed to rebuild state after a crash or to reproduce failures offline. Hooks allow injecting crash/recovery cycles and exporting telemetry so longevity, durability, and performance regressions can be investigated alongside functional bugs. The CLI also supports metamorphic option sets (e.g., toggling memory limits or bloom filters) to broaden the surface covered by a single fuzz run.

## What and how is it testing?
- **Randomized differential fuzzing.** `Harness.Run` spins in a fuzz loop, drawing weighted random operations (put, delete, get, range, and snapshot creation) with configurable key/value sizing, range limits, and snapshot reuse. Keys seen so far are tracked to bias reads toward existing data. Each operation is applied to RinDB and then cross-checked against the oracle, ensuring point reads, scans, and snapshot semantics match exactly.
- **Invariants over historical snapshots and iterators.** After every step the harness runs invariant checks covering monotonic snapshot reads, concatenation of adjacent range scans, and forward/backward iterator walks, catching bugs that simple equality checks might miss. Snapshot handles are recycled aggressively so that stale-handle management bugs surface quickly.
- **Stateful repro and crash resilience.** Operations are logged with their phase so the replay helper can rebuild reference state, finish partially completed operations, and resume sequences after crashes, letting developers deterministically reproduce issues discovered during fuzzing. Crash hooks in the CLI close and reopen both engines on a schedule to validate recovery code paths, while telemetry hooks report operation throughput for long-lived runs.
- **Running the harness.** Launch a fuzz session with `go run ./diffharness/cmd -n 100000 -log repro.jsonl`, optionally enabling metamorphic variants (`-metamorphic`), crash testing (`-crash-every=10000`), or OpenTelemetry export (`-telemetry-exporter-endpoint=localhost:4317`). A Docker Compose stack is provided to spin up an OTEL collector, Prometheus, Tempo, and Grafana if you want dashboards and traces while the harness runs. For quick regression checks, `go test ./diffharness/...` exercises the harness and oracle helpers through their unit tests.
